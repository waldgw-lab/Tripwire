---
name: Entity automation safety gates
description: Durable staging and migration decisions for role-first entity monitoring.
---
Entity discovery and live decision application are separate stages. Keep an
unconfigured provider operationally visible rather than provisioning paid usage
or treating unavailable extraction as declining relevance.

**Why:** The user requires explicit content authorization, hard budgets,
reviewed relevance calibration and actual private-publishing verification
before autonomous monitoring decisions; a shared workspace identity is not
authentication.

**How to apply:** Preserve the default observe-only staging, unknown source
independence, analyst pins and unresolved identities. Do not infer identities
from anonymous descriptions or appointments from the concept attachment.

The user selected a $1/day AI processing ceiling for the initial trial.

**Why:** The user approved this initial limit.

**How to apply:** Keep the initial trial within that ceiling; distinguish
conservative reservations from billed usage and measure actual costs before
recommending a different budget.

For this app, the user chose “openrouter or whatever mechanism replit uses to
connect an ai,” rather than a personal API-key connection.

**Why:** The user specified the managed connection route.

**How to apply:** Use Replit-managed provider provisioning; do not substitute a
personally billed API-key setup without the user's approval.

A model-proposed external identifier is an unresolved match suggestion, not a
validated link to the quoted subject, even if that identifier is already
verified elsewhere in the registry.

**Why:** A number or code may occur incidentally in a passage and match a
different entity's identifier. Exact value presence alone cannot establish who
it identifies.

**How to apply:** Keep extracted evidence/assertions on a separate discovery
candidate until a trusted subject-to-identifier link or an analyst identity
decision supports reuse of an established identity.

Use journaled additive SQL migrations for entity graph constraints, not schema
introspection push over those tables.

**Why:** The installed migration tool cross-joins composite foreign-key columns
while introspecting PostgreSQL and can propose dropping valid referenced
constraints or recreating existing indexes. Weakening workspace-scoped
relational integrity to accommodate that tool would be unsafe.

**How to apply:** Generate a new entity migration and apply it transactionally
through the existing migration runner. Never edit already applied SQL or drop
retained graph/history tables to repair schema drift.
